# Maintainer handbook – continuing from the repository alone

[← Documentation](index.md)

Everything needed to keep developing, testing and releasing Dissonance is in this repository. If every local copy is
gone, a fresh clone plus this page is enough – for a person or for an AI assistant (start by reading this page,
[development](development.md) and the [changelog](../CHANGELOG.md)).

Nothing about any particular installation (server names, addresses, accounts, login provider settings) belongs in
this repository. Keep that in your own, private notes.

## 1. Get going on a new machine

Requirements: `git`, Python 3.11+, Firefox (only for the browser tests), optionally Docker or Podman.

```bash
git clone https://github.com/wilderMann/dissonance.git && cd dissonance
python3 -m unittest test_ug2chordpro                      # should end with OK (some converter tests skip, see section 6)
mkdir -p /tmp/songs && SONG_DIR=/tmp/songs python3 app.py   # http://localhost:8080, single-user mode
python3 tests/browser/run.py                             # all browser tests, ~20 minutes
```

No other packages are needed for development: without Waitress the app uses Python's built-in server. Install
Waitress (`pip install --require-hashes -r requirements.txt`) to test the production server; the unit tests run
against it unless `TEST_SERVER=builtin`.

## 2. How the app is built

| Part | What it does |
|---|---|
| `app.py` | The whole backend: one request class whose `route()` dispatches on method and path, used by both the WSGI app (Waitress) and the built-in `http.server`. JSON API under `/api/…`, static files from the `STATIC` table, `/healthz`. |
| SQLite (`SONG_DIR/.liederbuch.db`) | One connection, one writer at a time (`tx()`), schema in `SCHEMA` plus small `ALTER TABLE` migrations in `tx()` – new columns are added there so old databases upgrade on start. Song texts are stored once per content hash (`blobs`, like git objects), every save adds a row to `versions`. |
| `.cho` files | The source of truth for songs. The database keeps stable song ids, history and everything else. Changes made outside the app (file share, editor) are noticed by comparing modification times and recorded as versions. Deleted/renamed files go to `.papierkorb/` (trash) with a timestamp. Saving checks the file's modification time to detect conflicting edits. |
| `auth.py` | OpenID Connect (authorization code flow, PKCE). Users are identified by the provider's `sub`; sessions are random tokens, stored hashed. |
| `i18n.py` | Server messages: German text is the key, English translation in a table, chosen per request (`X-Lang` header from the app, `lang` cookie, `Accept-Language`). |
| `ug2chordpro.py` | Converters from Ultimate Guitar / Ukulele-Tabs.com pages and "chords over lyrics" text to ChordPro. |
| `index.html` | The whole interface – HTML, CSS and JavaScript in one file, no build step, no framework. Hash routes (`#/lied/<file>`, `#/buch/<id>`, `#/bearbeiten/<file>`, `#/server`, …). |
| `sw.js` | Service worker, network first with a cache fallback (offline use). The cache name contains the version; the server fills in `__VERSION__` when it serves the file. |
| `chords.json` | Chord tables from ChordPro, generated by `tools/chordpro_chords.py` – never edit by hand. |

Important rules in the code:

- **Two modes**: without `OIDC_ISSUER` the app is single-user (`OIDC is None`, every request acts as a local admin);
  features that need several people (private items, share links, campfire mode, collaborators) are hidden in the UI
  (`body.noauth .needs-auth`) and refused by the API. Check both modes for every change that touches rights.
- **Rights** are checked on the server for every request; the UI only hides what you may not do
  (`needs-user`, `needs-edit`, `needs-manage`, `needs-auth` classes).
- **Texts**: every user-visible text is written in German and translated with `$t("…")` (or picked up from the static
  HTML) through the English table `I18N_EN` in `index.html`; server messages go through `i18n.py`. Every new German
  text needs its English entry – `tests/browser/test_english.py` fails on German left in the English interface.
- **Settings in the browser** are stored in `localStorage` with the prefix `lb.`.
- **No new dependencies.** Standard library plus Waitress; no build tools. This keeps the image small and the project
  maintainable by one person.
- **Data safety**: never write outside `SONG_DIR`; writes are atomic (temporary file + rename); with `REQUIRE_DB=on` the
  database is never created, so an unmounted folder fails loudly instead of starting empty.

## 3. Tests

- `test_ug2chordpro.py` – converter, API, rights, login against a fake OpenID provider (`FakeKeycloak`), languages,
  start-up guards. Run it with both servers: `python3 -m unittest test_ug2chordpro` and
  `TEST_SERVER=builtin python3 -m unittest test_ug2chordpro`.
- `tests/browser/` – real browser tests in headless Firefox, driven over Marionette (`browser.py`, no Selenium).
  `run.py` lists every test with its window widths and server kind: `app` (single-user), `login` (fake provider via
  `login_server.py`; which user logs in is set by writing claims to `SONG_DIR/.who.json`) and `login-noguest`
  (`GUEST_ACCESS=off`). Headless Firefox windows are at least 500 px wide, so phone widths are simulated with browser
  zoom. Each run gets a fresh copy of the invented songs in `tests/browser/fixtures/`.
- Run a single test: `python3 tests/browser/run.py test_play --width 390 -v`. Screenshots and PDFs land in
  `tests/browser/out/` (not committed).
- When you move or rename a button, search the tests for its id – several tests click elements directly.

## 4. Making a change

1. Change the code; keep German UI keys with English translations.
2. Add or adjust tests; run the unit tests (both servers) and the browser tests.
3. If the interface changed visibly, regenerate the README screenshots: `python3 tools/screenshots.py`.
4. Update the documentation in `docs/` and note the change in `CHANGELOG.md` under a new version.

## 5. Releasing

1. Put the new version in `VERSION` ([semantic versioning](https://semver.org/): fix → `1.0.1`, feature → `1.1.0`,
   anything that needs users to change their setup → `2.0.0`) and add its section to `CHANGELOG.md`
   (`## [1.1.0] – YYYY-MM-DD`).
2. Commit and push, then `git tag v1.1.0 && git push origin v1.1.0`.
3. The workflow `.github/workflows/release.yml` checks that tag and `VERSION` match, runs the unit tests, builds the
   image for amd64 and arm64, pushes it to `ghcr.io/<owner>/dissonance` (tags `1.1.0`, `1.1`, `1`, `latest`) and
   creates the GitHub release with the changelog section as notes. It needs no secrets of its own – it uses the
   automatic `GITHUB_TOKEN`.
4. The GitHub actions in the workflow are pinned to commit hashes (the version is in a comment). To update one, look up
   the commit of its newest release tag and replace hash and comment.

If the repository is ever recreated: images on ghcr.io start private – make the package public once
(Packages → dissonance → Package settings → Change visibility).

## 6. What is deliberately not in the repository

- **Saved pages from Ultimate Guitar / Ukulele-Tabs.com** (`examples/`, ignored by git): they contain other people's
  copyrighted lyrics. A few converter tests use them and are skipped without them. To run those tests, save a few song
  pages from these sites into `examples/` yourself ("Save page as…", complete HTML).
- **Real songs and databases**: `*.cho` and `*.db` are ignored except the invented test songs.
- **Anything about a specific installation**: compose files with real addresses, login provider settings, secrets.
  The repository's `docker-compose.yml` is a generic example with placeholders.

## 7. Chord tables

`chords.json` comes from the ChordPro reference implementation (Artistic License 2.0). Update it with
`python3 tools/chordpro_chords.py` (newest ChordPro release) and commit the diff; `--check` only reports whether
anything changed. The app verifies every shape when it loads the table and skips shapes that do not fit their name.
